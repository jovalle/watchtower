# Watch Together implementation research and handoff

Research date: 2026-09-27. Inspected repository HEAD: `8578769ae3273a5918910b769053d494c56c7ae6`. This is supporting research, not a normative protocol or a claim that the feature exists or has passed live tests. The shared web/Android contract delivered with this handoff is normative for implementation; if this research differs, follow that contract and update the research. Use its final field names and lifecycle policies when producing validated fixtures; this research explains the evidence and integration hazards rather than defining alternatives. Paths below are relative to the Watchtower repository. Every numerical policy below is a proposed starting value, to be measured and adjusted, unless identified as existing behavior.

## Product boundary and primary evidence

Plex's own support search result contains a dated 2025-02-25 announcement ending Watch Together support in its new experience. This supports building an independent Watchtower synchronization feature; it does not prove that every Plex client lost the feature on the same date or explain every current Plex bug. Direct page retrieval returned HTTP 403 during this research, so treat the indexed announcement as the verified scope of that claim. [Plex Watch Together](https://support.plex.tv/articles/watch-together/).

Build shared playback of authorized personal-library movies and episodes through Watchtower's existing stream pipeline. Every member authenticates independently and must already have access to the selected item. No shared owner token, rebroadcasting, Plex cloud Watch Together dependency, or Netflix content integration. Plex documents per-library access and restrictions, including content-rating and label restrictions. A room invitation is not media access. [Plex library access](https://support.plex.tv/articles/201105738-creating-and-managing-server-shares/).

Remote playback requirements can vary by account/server entitlement and client. Preserve upstream errors; do not claim an entitlement workaround or universal free remote playback. [Plex remote playback requirements](https://support.plex.tv/articles/requirements-for-remote-playback-of-personal-media/).

## Required user experience

1. Movie/episode detail action creates a private room after access validation. Show selected title, host, start position, participant readiness, and invitation controls.
2. Invite link joins a lobby only after login and per-user item authorization. Use an unguessable invite secret distinct from public room identity. Support host rotate/revoke, expiry, and explicit room close. Avoid logging invite secrets; prefer URL fragment followed by authenticated POST redemption, with no invite token in analytics or referrer headers.
3. Host chooses beginning or their own saved position on creation; thereafter room state is authoritative. Other members' saved progress never moves the room.
4. Members prepare independent streams and explicitly become Ready. Display loading, ready, autoplay blocked, buffering, reconnecting, unauthorized, and incompatible states separately.
5. Host-only shared controls: play, pause, seek, intro/credits skip, next episode (an arbitrary episode picker requires the separately validated command described in the shared contract), transfer host, remove member, close room, rotate invite. Other members control their own volume, audio track, subtitles, quality, fullscreen and accessibility settings. Explain disabled shared controls accessibly.
6. Default pause-on-buffering behavior: a participating active viewer's sustained buffering freezes the room at its current authoritative position. Show blocker names and reason. Do not automatically resume just because buffering stopped; host resumes explicitly once ready. A bounded timeout removes a stalled viewer from the readiness barrier (not from authentication or room membership) and offers retry. Host can wait or exclude a blocker. Late joiners never unexpectedly pause an already-playing room; they catch up first and enter the active barrier only after ready acknowledgement.
7. Host disconnection pauses the room and opens a 30-second reconnect grace. After grace, the server transfers host to the earliest-joined connected ready participant, or ends the room if none qualifies. Explicit host Leave performs this transfer immediately; explicit End closes the room for everyone. Use a server-assigned join ordinal with participant-ID tie-break so election is deterministic, and invalidate commands from the former host atomically. The grace begins at server disconnection detection after 15 seconds of stale authenticated presence, not at a client-reported time.
8. End-of-item and next-episode changes are one authoritative transition. Enter preparation for the next item and reset readiness. Follow the shared `resumeAfterPrepare` intent and scheduled-start rules rather than independently advancing clients. Authorize the host and every member before committing the next item: host denial leaves the old item paused; remove denied members before broadcasting new protected metadata, send only a terminal access-denied envelope without next-item details, and close their subscriptions. The shared countdown exposes only its deadline, not target identity/title/art. Personal auto-next and auto-intro preferences cannot independently move room participants. A host intro-skip becomes one room seek.
9. Leaving stops only the leaver's playback session, persists their actual position, and removes their blocker. Offer explicit Continue Solo with actual current position; never silently detach and continue advancing during control disconnection.
10. Room panel works with keyboard, visible focus, screen reader labels, status announcements without per-second chatter, touch, and narrow viewports. Room controls cannot trap focus or cover captions.

## Minimal architecture and ownership

Use authenticated POST commands plus a private SSE stream carrying full snapshots. Room server/reducer is authoritative and web/Android clients share exactly the same contract. There is no requirement to replay a command/event log: a complete current snapshot is enough to recover current playback intent. Server command processing still needs serialized order and idempotency.

Watch Together agent owns the room domain, reducer, room API, room web UI, and browser playback integration. Android agent owns native device authorization, `/api/v1` JSON playback facade, capability negotiation, and Kotlin client. Both coordinate thin shared auth/playback helper extraction before editing shared files. Neither creates a second room protocol or independently rewrites the player backend.

Initial deployment may use bounded in-memory room maps in the existing single Node process, with immediate fan-out after a mutation and scheduled lease checks. Document restart semantics: rooms expire, clients pause and show room-ended/rejoin guidance. Never pretend local maps work across replicas; deployment must remain one authoritative process. Before horizontal scaling or seamless restart recovery, use transactional shared state and pub/sub. Sticky sessions alone are not state consistency. Do not add Redis solely speculatively.

Proposed limits: 8 active playback participants per room, 100 concurrent rooms, 24-hour maximum room lifetime, 30-minute empty-room cleanup, 16 KiB command bodies, finite bounded payload strings, and bounded idempotency cache. Tune against Plex transcoder capacity. Keep limits centralized and documented; server enforces them independently of UI.

## Protocol v1: required wire invariants

All positions and durations are nonnegative finite integer **milliseconds of the full media item**, never segment-relative offsets. Identify content as `{ serverMachineId, ratingKey, mediaId, partId }`; a rating key is only meaningful within one server. Start with the same configured server/item/media edition for all users. Do not match different cuts by title or silently equate durations. Multi-server and alternate-edition alignment are separate future features.

A full snapshot contains at least:

- `protocolVersion`, unique non-reused `roomId`, `epoch` (random coordinator process-instance ID), `revision` (increasing control-state integer), and separate `presenceRevision`, `serverNowMs`.
- Host participant ID; lifecycle (`lobby`, `preparing`, `paused`, `playing`, `ended`); pause reason; content identity; metadata duration; canonical position anchor and server-clock anchor; playback rate fixed at 1 for v1.
- Participant public ID/display name and safe statuses; no email/token/stream URL. A participant is one playback device membership, not merely an account. Multiple authenticated devices belonging to the same account may participate independently. Bind each participant to a server-issued device session and scope stream replacement generations to that device/player. A reconnect recovers that membership; an explicit replacement invalidates the old membership version. Shared Plex progress may still be last-accepted observation for that account; do not promise separate histories per device.
- Separate `mediaGeneration` and `preparationGeneration`, `resumeAfterPrepare`, and deadline-only `nextCountdown`, with membership and safe status/error fields as defined in the shared schema. Do not invent a competing snapshot shape.

Command envelope follows the shared contract: `commandId` UUID, `commandSequence`, `membershipVersion`, `epoch`, `mediaGeneration`, `expectedRevision`, and a bounded type-specific payload. Server derives the actor and role from authenticated membership; caller-supplied participant IDs never prove identity. Commands and presence must match the current identity context. Native requests carry `X-Watchtower-Identity-Version`; browser adapters provide equivalent effective-identity invalidation. Capture the principal immutably and recheck identity/generations after awaited authorization and before side effects.

Use the normative `/api/v1/rooms` and `/api/v1/clock` routes in the shared contract. Freeze concrete validated JSON fixtures jointly with the native agent before implementation; do not invent parallel route families. API errors are JSON with stable codes and HTTP status (400 malformed, 401 authentication, 403 forbidden, 404 missing/concealed room, 409 stale revision/epoch, 410 expired, 422 unsupported media/negotiation, 429 rate limit, 503 upstream unavailable). Do not return a login HTML page to an SSE or JSON client.

Shared control commands follow the contract: `play`, `pause`, `seek`, `select-next`, `cancel-next`, `transfer-host`, `remove-participant`, `end`, and validated room-policy changes. Ready/not-ready and local state/position/error belong to presence reports, with `presenceSequence`, `membershipVersion`, `epoch`, `mediaGeneration`, `preparationGeneration`, the currently registered owned `playbackSessionId`, and bounded observed status fields. Leave uses its idempotent endpoint. Telemetry cannot arbitrarily alter room media/host. Server can derive a buffering pause from an authorized active participant report under the defined policy.

Under the room lock/serialized reducer: validate identity, membership lease, role, `mediaGeneration`/`preparationGeneration`, epoch; check existing command ID after current authorization and before optimistic revision validation; compare duplicate request digest and return original outcome (different payload under reused ID is an error); reject stale expectedRevision for shared controls with current snapshot; apply one valid transition; increment revision exactly once; retain bounded command result; broadcast snapshot. Independent membership telemetry sequence avoids unrelated heartbeat updates constantly conflicting with host commands; keep `revision` separate from `presenceRevision` as the contract requires. In-flight Plex access checks must re-check mediaGeneration and `preparationGeneration` under lock before committing, so a slow authorization response cannot overwrite a newer selected item.

Client serializes its own control intents. On a lost response, retry the same command ID, sequence and body. Retain the membership's highest accepted command sequence even after bounded result-cache eviction: an older accepted sequence without a retained result returns `409 command_result_expired` and never executes again. A stale-revision conflict requires a fresh action and sequence. Never replay old seeks after reconnect.

Create/join/invite rotation have their own retry envelope: `requestId`, current process `epoch`, and server-clock `expiresAtMs` at most 60 seconds ahead. Cache identity/device/request-scoped digest and result through expiry, reject changed payloads or expired requests, and reject admission rather than evicting an unexpired deduplication entry. Join retry recovers the same membership. After losing a response, retry the identical still-valid request or recover current membership; do not blindly issue a fresh create.

Create/join/authenticated membership recovery returns `participantId`, `membershipVersion`, `nextCommandSequence`, and `nextPresenceSequence` alongside the snapshot. Recover both counters after reload; old/equal presence sequences are ignored. Distinct devices may share an account, but one authenticated device context has one active room player. Browser tabs sharing a device cookie must explicitly take over or reuse it, invalidating prior connection/player generations. A registered replacement owned playback session becomes current before readiness; old-session callbacks cannot clear new blockers. Global barrier reset changes `preparationGeneration`; content/edition/timeline replacement changes `mediaGeneration`.

SSE always sends complete latest snapshot upon authorized connect/reconnect, then on state change. `id` may encode epoch/revision for diagnostics, but `Last-Event-ID` does not imply a retained event log. State explicitly that replay is unsupported and reconnect is a fresh snapshot. Clients apply control revision and presenceRevision independently and reject regressions within each counter in the same epoch; an unchanged control revision does not discard a newer presence update; a different process epoch expires the old room and requires an authenticated newly created room handshake. Register subscriber and capture snapshot atomically to avoid a missed mutation window. Close listeners/timers on abort, removal, logout/revocation, room expiry, or shutdown. Slow clients receive latest coalesced state or disconnect; never accumulate an unbounded queue.

SSE has standard reconnect and Last-Event-ID behavior, UTF-8 event framing, and comment heartbeat support; native EventSource does not expose arbitrary authorization headers. Browser same-origin cookies work; native clients use their authorized HTTP stack. Ensure the frontend interprets non-SSE auth failures and does not reconnect forever to login HTML. [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html).

Proposed heartbeat defaults from the shared contract: named SSE `heartbeat` events with epoch/server time at most every 5 seconds, or authenticated presence-response acknowledgements; participant heartbeat every 5 seconds; client staleness threshold 15 seconds; host grace 30 seconds after stale-presence detection; blocker grace 30 seconds. Event names are `snapshot`, `heartbeat`, and `ended`; normal room `ended` includes its final authorized snapshot. An access-denied termination reveals no protected next-item details. Optional comment pings are transport keepalives only and cannot prove liveness to browser JavaScript. No keepalive refreshes authorization. Re-check membership for every emitted snapshot and command; use short bounded authentication revalidation for long-lived streams, with explicit revocation/logout invalidation where available. Room lifecycle timers use server time and are not driven solely by client clocks.

## Clock and playback synchronization

Use one process-relative monotonic millisecond server clock, e.g. Node `performance.now()`, and the shared `epoch` on process start. Do not send raw monotonic values without clock identity; do not subtract browser `performance.now()` directly from server `performance.now()` or wall `Date.now()`. Browser High Resolution Time exists specifically to measure monotonic durations independent of wall-clock adjustments. [W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/).

The shared contract uses a four-timestamp probe: client local monotonic send `c0` and receive `c3`; server monotonic `receivedAtMs` (`s1`) and `sentAtMs` (`s2`) plus process `epoch`. Estimate server-minus-client offset as `((s1-c0)+(s2-c3))/2` and network RTT as `(c3-c0)-(s2-s1)`. Reject implausible samples, prefer low-RTT samples, and retain uncertainty. Estimate server now as local monotonic now plus offset. Resample after foreground, network change, resume, reconnect, and periodically. This assumes roughly symmetric network latency and is an estimate, not proof of exact synchronization. If uncertainty is excessive, show catching-up and avoid repeated correction thrash.

For playing snapshots, target position = clamp(anchor.positionMs + max(0, estimatedServerNowMs-anchor.effectiveAtMs), 0, durationMs). For paused snapshots, target = anchor.positionMs. Compute the current authoritative position before every pause/seek/media change. Host Play schedules a future `anchor.effectiveAtMs` with a proposed 1,000 ms lead once required participants are ready. Stay paused until that time; the clamped target formula alone must not cause early playback. A higher revision cancels or supersedes any scheduled start. Late receipt applies the current target rather than restarting at the old anchor. Seek while playing enters preparing with `resumeAfterPrepare=true` and automatically schedules its already-requested continuation after readiness. Seek while paused sets it false and remains paused. Any newer explicit pause clears continuation intent. Ordinary buffering or host-loss pause also clears it and requires fresh host Play. Every group pause freezes the authoritative position evaluated at acceptance time, not the old playing anchor position.

Proposed correction policy: ignore drift under 250 ms; optionally adjust rate gently (0.97–1.03) for 250–1500 ms drift only on verified supporting paths; seek above 1500 ms or when paused off-target. Rate correction is optional and can be skipped if precise seeks meet targets; always restore rate 1 on pause/leave/disconnect/error. Rate changes and seeking cannot produce new room intents. Cap correction frequency (e.g. at most one hard seek per 5 seconds outside explicit host seek) and implement hysteresis. These are hypotheses for a device/network test matrix, not measured guarantees.

In browsers, `play()` is asynchronous and may be rejected by policy; `waiting`, `playing`, `seeking`, `seeked` and `ended` describe different conditions. Use a visible user-gesture Join/Ready flow and report blocked autoplay, not fake readiness. [HTML media specification](https://html.spec.whatwg.org/multipage/media.html#dom-media-play).

Android must map Media3 `playWhenReady`, buffering state, and `isPlaying` separately: intended play is not proof of advancing playback. [Media3 player events](https://developer.android.com/media/media3/exoplayer/listening-to-player-events).

Critical HLS check: current browser code assumes full-item `currentTime` when reporting and seeking; Plex offset manifests may have timestamp behavior dependent on the chosen pipeline. Verify direct file, direct-stream HLS, transcoded HLS, native HLS, and Media3 using a nonzero initial offset and an out-of-buffer seek. Define a tiny mapping from player timeline to canonical item milliseconds only if observed timestamps require it. Do not blindly add the resume offset (double counting) or blindly assume zero origin. Use metadata duration, not padded HLS duration. Record evidence. Wrong timeline mapping corrupts both synchronization and user progress.

## Browser integration hazards and required controls

- Keep coordinator/membership above `VideoPlayer key={streamUrl}` or in route-level stable context. Remounting a media source must not create a new room or reset event revision/command deduplication.
- Trace every caller before introducing shared intent helpers: play button, video click, Space/K, media keys if present, skip buttons, Arrow keys, progress drag/touch, slider keyboard, iOS fullscreen controls, intro skip, autoplay-next, episode panel, quality selection, retry/transcode fallback, track changes, stream reload, Back/pagehide.
- Distinguish local user intent from applying server state. A transient boolean cleared immediately after setting `currentTime` is insufficient because media events are asynchronous. Correlate expected effects/generation, and make reconciliation idempotent. Tests must catch remote pause causing a fresh command or an infinite seek loop.
- Host native controls become commands. Participant native seek/play controls must be reconciled to authoritative state with clear UI; if a platform cannot reliably enforce this, explicitly mark that mode unsupported for synchronized playback rather than claiming parity.
- On stream reload while room remains playing, latest room target is recomputed after readiness; stale original reload target is not used indefinitely. On paused room, `canplay` never forces playback.
- Local volume/in-player track changes never cause a group pause. For deliberate quality/track source replacement, first obtain an authenticated acknowledgement making that participant temporarily nonblocking and unready, then replace its owned source. The room continues; rejoin the barrier only after proven readiness at the latest target. This transition cannot undo an existing group buffering pause. Unexpected buffering of an active blocker still triggers the defined group pause.
- External casting/remote playback needs receiver telemetry/control to synchronize reliably. Existing cast availability is not evidence of sync support. Disable room casting or clearly label unsupported until tested with a receiver implementation; same caution for OS-managed background playback and suspended tabs.
- Do not conflate room end with scrobbling everyone as watched. Existing player reports its own observed end and actual time; preserve that behavior independently per participant. The host advancing early cannot mark every participant complete.

## Security and operational requirements

Authenticated membership and item-level Plex authorization are required for create/join, snapshots, commands, new-media transitions, and streams. Authorize with each user's server token; never accept a client's claimed media-access boolean. Short-lived membership/access leases provide a bounded revocation interval; validate again after changes to identity/server/content. Protect tokens and invitation secrets from client bundles, payloads, URLs, logs, exception text, fixtures, and telemetry.

Cookie-authenticated mutation routes need explicit CSRF protection (exact allowed Origin validation and appropriate token/header strategy), JSON content-type validation, request size limits, and no mutation through GET. SameSite=Lax alone is not a complete CSRF design. Native bearer-authenticated endpoints have a separate explicit policy; absence of Origin is not authorization. Account for reverse proxies using a configured canonical origin; don't trust arbitrary forwarded hosts. [OWASP CSRF](https://community.owasp.org/attacks/csrf).

Validate every enum, number, ID length, revision and membership lease. Rate-limit invite redemption by account and trustworthy client address, and control commands per member/room. Invitation revocation prevents new joins; member removal independently invalidates active membership. Bound participants, subscriptions per member, command cache, queues, timers, and rooms. No unbounded room enumeration. Redact private titles from metrics when unnecessary.

For reverse proxies, disable SSE buffering/compression where needed, use `Cache-Control: no-store, no-transform`, appropriate stream content type, and test actual production ingress idle timeouts. Existing Node server is Express without a room push layer. Load test proxy streaming, not only Remix unit responses. Shutdown closes streams, stops per-user sessions best-effort, and rejects further commands cleanly. Admission capacity accounts for independent Plex streams and CPU/egress.

## Acceptance tests: required evidence, not promises

No universal frame-perfect promise.

## Final contract reconciliation

The review decisions are resolved in [the shared contract](../shared-contract.md): separate preparation/media/identity/membership generations; restored command and presence sequences; observable heartbeats; four-timestamp clock sampling; 30-second host grace after server stale-presence detection with stable join-order election; scheduled continuation only for retained play intent; pre-broadcast removal of next-item-ineligible members; deadline-only countdowns; nonblocking deliberate local source replacement; and bounded expiry-aware mutation idempotency. Implement the shared fixtures and test these invariants rather than reopening them independently in each client.
